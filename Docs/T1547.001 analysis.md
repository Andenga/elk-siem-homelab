# Assessment of MITRE ATT&CK T1547.001: Registry Run Keys / Startup Folder Using Atomic Red Team

## 1. Executive Summary

This report presents an assessment of a Windows-based adversary-emulation exercise targeting **MITRE ATT&CK technique T1547.001, Registry Run Keys / Startup Folder**. The exercise was executed using **Atomic Red Team** through PowerShell with the command:

`Invoke-AtomicTest T1547.001`

The objective of the exercise was to simulate multiple mechanisms that an adversary could use to establish **persistence** or achieve automatic execution on a Windows system. MITRE ATT&CK classifies T1547.001 under **T1547, Boot or Logon Autostart Execution**, and associates the technique primarily with the **Persistence** and **Privilege Escalation** tactics. The technique covers both Registry-based autostart mechanisms and Windows Startup Folder mechanisms.

The supplied output shows that a large number of Atomic Red Team tests executed successfully. These included modifications involving Registry Run keys, RunOnce, PowerShell, VBS/JSE/BAT startup files, startup-folder configuration, policy-based Run keys, Winlogon configuration, `secedit`, `BootExecute`, RDP logon behavior, Windows context-menu persistence, and a Turla Mosquito-inspired Run-key technique. The output confirms successful execution of many individual tests, but it **does not by itself establish that the machine was compromised, that malware was present, or that security controls successfully detected the activity**.

Most tests returned an **exit code of 0**, indicating successful completion of the corresponding Atomic Red Team test. Two notable tests returned **exit code -1** after timing out or repeatedly prompting for overwrite confirmation. The RunOnce test and Boot Verification Program test therefore require additional interpretation rather than being classified simply as successful or unsuccessful.

The exercise is important from a defensive-security perspective because the tested mechanisms abuse legitimate Windows functionality. Registry keys and Startup Folders are normal components of Windows, meaning defenders cannot simply block the underlying functionality. Instead, effective detection must identify **unusual modifications, suspicious paths, unexpected executables or scripts, abnormal parent-child process relationships, and changes followed by execution**. MITRE's current detection guidance similarly emphasizes correlating Registry/startup modifications with unusual binary paths, script-based payloads, and subsequent process execution.

Overall, the exercise demonstrates broad coverage of T1547.001 and provides a useful foundation for **purple-team validation, detection engineering, threat hunting, EDR/SIEM testing, and security monitoring improvement**. However, additional telemetry would be required to determine whether the organization's defensive controls actually detected the simulated behaviors.

# 2. Introduction

Modern cyber attacks frequently depend on maintaining access to a compromised system after the initial intrusion. An attacker who successfully executes code once may lose access when the system reboots or the user logs out. **Persistence** addresses this problem by establishing a mechanism through which malicious code can automatically execute again.

Windows provides numerous legitimate mechanisms for automatically starting applications. These mechanisms include Registry Run keys, Startup Folders, policy settings, Winlogon configuration, and other boot or logon mechanisms.

Because these features are legitimate operating-system functionality, an attacker can abuse them without necessarily introducing an obviously malicious mechanism.

MITRE ATT&CK identifies this behavior as **T1547.001 — Registry Run Keys / Startup Folder**. MITRE describes the technique as an adversary adding a program to a startup folder or referencing it through a Registry Run key so that the referenced program executes when a user logs in. The program normally executes within the security context of the relevant user.

The exercise examined in this report used Atomic Red Team to emulate these behaviors in a controlled manner.

# 4. Background

## 4.1 MITRE ATT&CK

MITRE ATT&CK is a knowledge base describing adversary tactics, techniques, and procedures observed or modeled in real-world cyber operations.

The ATT&CK hierarchy is particularly useful because it provides a common language for describing attacker behavior.

For this assessment:

**Tactic → Technique → Sub-technique**

* **Persistence / Privilege Escalation**

  * **T1547 — Boot or Logon Autostart Execution**

    * **T1547.001 — Registry Run Keys / Startup Folder**

MITRE currently identifies T1547.001 as a Windows technique under Boot or Logon Autostart Execution.

---

## 4.2 Registry Run Keys

The Windows Registry is a hierarchical configuration database used by the operating system and applications.

Several Registry locations can cause programs to execute automatically.

Important examples include:

* `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`
* `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce`
* `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`
* `HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce`

MITRE identifies these as standard Windows Run/RunOnce locations associated with T1547.001.

### HKCU versus HKLM

**HKCU — HKEY_CURRENT_USER**

This generally affects the currently logged-in user.

**HKLM — HKEY_LOCAL_MACHINE**

This contains machine-wide configuration and can affect users across the system. Consequently, modification of HKLM often has greater privilege implications.

This distinction is important for defenders because a persistence mechanism in HKCU may be established with fewer privileges than one requiring modification of HKLM.

---

## 4.3 Run versus RunOnce

The `Run` and `RunOnce` mechanisms are conceptually different.

A **Run** entry is designed to cause an application to execute whenever the relevant startup/logon condition occurs.

A **RunOnce** mechanism is intended for one-time execution.

From an attacker's perspective, either mechanism can be useful depending on the objective. A Run key may provide recurring persistence, whereas RunOnce can support execution during a particular stage of an operation.

---

## 4.4 Startup Folder

Windows also provides Startup Folders.

MITRE identifies both a user-specific Startup Folder and a system-wide Startup Folder. Programs or shortcuts placed in these locations can be launched when the relevant user logs in.

This is important because an attacker does not necessarily need to modify a Registry Run key to achieve startup execution.

## 5.3 Interpretation of Exit Codes

For this assessment:

* **Exit code 0** = the Atomic Red Team test reported successful completion.
* **Exit code -1** = the test did not complete normally according to the test runner.

Importantly, an exit code of 0 does **not** mean:

> "The computer was successfully compromised."

It means that the test itself completed successfully.

Likewise, an exit code of -1 does not necessarily mean that the underlying security behavior could never occur. It may indicate an environmental, interactive, timeout, or test-execution problem.

# 9. Security Significance

## 9.1 Persistence

The primary security significance is persistence.

An attacker who already has execution on a Windows machine may attempt to configure the operating system so that their code executes again during a future logon or startup event.

This increases the attacker's ability to survive:

* reboots;
* user logoffs;
* routine administrative activity;
* some forms of remediation.

---

## 9.2 Abuse of Legitimate Functionality

A major lesson from this exercise is that the attacker does not necessarily need to exploit a software vulnerability.

Instead, the attacker may abuse a legitimate Windows feature.

This creates a difficult defensive problem.

Blocking the Registry would be impractical.

Blocking Startup Folders would disrupt legitimate software.

Blocking PowerShell entirely would also be impractical in many enterprise environments.

Therefore, security teams need to identify **suspicious use of legitimate mechanisms**.

---

# 10. Detection Recommendations

MITRE's current detection strategy for T1547.001 recommends correlating Registry/startup modifications with unusual binary paths or script-based payloads and subsequent process execution or abnormal process relationships.

Based on the exercise, the following controls are recommended.

## 10.1 Monitor Registry Modification

Monitor modifications to known autostart locations, including:

* `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`
* `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce`
* `HKLM\Software\Microsoft\Windows\CurrentVersion\Run`
* `HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce`
* Explorer policy Run locations
* Winlogon values
* Startup Folder configuration
* `BootExecute`

A Registry modification should be especially suspicious when the resulting command points to:

* `%TEMP%`
* `%APPDATA%`
* `%LOCALAPPDATA%`
* user-writable directories
* newly created files
* scripts
* unsigned binaries
* unusual DLLs.

---

## 10.2 Correlate Registry Changes With Process Execution

A Registry change by itself may be legitimate.

A stronger detection is:

**Registry modification → suspicious file/process → execution**

For example:

1. PowerShell modifies a Run key.
2. The Run key references a file in a temporary directory.
3. The referenced file executes at logon.
4. The process creates a network connection.

The combined chain is significantly more suspicious than any individual event.

---

## 10.3 Monitor PowerShell

The exercise specifically demonstrates PowerShell being used in Registry persistence.

Recommended telemetry includes:

* PowerShell process creation;
* command-line logging;
* Script Block Logging where appropriate;
* suspicious encoded commands;
* unusual parent processes;
* PowerShell writing to Registry autostart locations.

---

## 10.4 Monitor Windows Script Host

The VBS and JSE tests demonstrate why Windows Script Host deserves monitoring.

Relevant execution involving:

* `cscript.exe`
* `wscript.exe`
* `.vbs`
* `.jse`

should be correlated with Startup Folder activity.

---

## 10.5 Monitor Startup Folder Changes

Security monitoring should identify newly created or modified files in:

* user Startup Folders;
* system-wide Startup Folders.

Particular attention should be given to:

* `.lnk`
* `.vbs`
* `.jse`
* `.bat`
* `.cmd`
* executables
* DLL-related execution mechanisms.

---

## 10.6 Monitor Winlogon

Changes to Winlogon `Shell` and `Userinit` values should be treated as high-value security events.

These values are closely associated with the Windows logon process.

A detection rule could prioritize:

> Any unexpected modification to Winlogon startup configuration by a non-standard administrative process.

---

## 10.7 Monitor BootExecute

Because `BootExecute` is involved in early Windows startup, changes should be monitored carefully.

The normal configuration should be baselined, and deviations should generate high-priority alerts where appropriate.

---

## 10.8 Use Process Trees

Process-tree analysis can significantly improve detection.

Instead of asking:

> "Did rundll32.exe execute?"

ask:

> "Why did rundll32.exe execute?"

For example:

`explorer.exe → rundll32.exe → suspicious.dll`

may be much more informative than simply detecting `rundll32.exe`.

Similarly:

`powershell.exe → registry modification → logon → suspicious process`

provides a meaningful behavioral chain.

# 11. Threat-Hunting Recommendations

A threat hunter investigating T1547.001 should ask:

### Registry

* What new Run keys were created recently?
* Which existing Run keys changed?
* Are any values pointing to user-writable directories?
* Are executable paths unusual?
* Are scripts referenced?
* Were the changes made by PowerShell or another scripting interpreter?

### Startup Folder

* What files were recently added?
* Were any shortcuts created?
* What do the shortcuts point to?
* Who created them?
* Was the creating process unusual?

### Winlogon

* Have `Userinit` or `Shell` values changed?
* Were they modified outside a known administrative change?

### Boot

* Has `BootExecute` changed?
* Does the new value correspond to an approved Windows component?

### RDP

* Did the persistence event occur around an RDP session?
* Was the user expected to establish that session?

### Process Relationships

* What process performed the modification?
* What process subsequently executed?
* Was the parent process expected?

# 16. Discussion

The most important finding from this exercise is not simply that Windows contains many persistence mechanisms. It is that **persistence can be achieved through ordinary operating-system functionality**.

An attacker does not necessarily need to install a conventional service or exploit a vulnerability.

They may instead modify an existing configuration mechanism.

This creates a fundamental defensive challenge.

Traditional security thinking might focus on identifying malicious files. However, the behavior demonstrated by this exercise shows why defenders must also monitor **configuration changes and execution context**.

For example, the following individual events may each have legitimate explanations:

* PowerShell executes.
* A Registry key changes.
* `rundll32.exe` runs.
* A `.vbs` script executes.
* A shortcut is created.

The security significance increases substantially when these events occur together in a suspicious sequence.

Therefore, the strongest defensive strategy is behavioral correlation.

The exercise also illustrates the value of adversary emulation. Rather than asking theoretically whether a detection rule should work, security teams can execute a controlled simulation and determine whether the actual monitoring architecture observes it.

This makes Atomic Red Team useful for **purple teaming**, because the offensive behavior and defensive telemetry can be evaluated together.

# 17. Real-World Importance

T1547.001 matters because persistence is a major component of long-running intrusions.

Consider the following simplified attack lifecycle:

**Initial Access → Execution → Persistence → Discovery → Credential Access → Lateral Movement → Collection → Exfiltration**

Persistence sits between initial execution and longer-term control.

If an attacker cannot survive a reboot or logoff, their foothold may disappear.

If they can establish reliable autostart execution, they have a greater opportunity to maintain access and continue subsequent stages of the intrusion.

The technique therefore has importance beyond the individual Registry modification.

It can become an enabling mechanism for an entire intrusion.

MITRE explicitly notes that adversaries can use these configuration locations to execute malware, including remote-access tools, and maintain persistence through system reboots.
